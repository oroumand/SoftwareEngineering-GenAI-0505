## اصل اول: استفاده یکپارچه از دات‌نت ۱۰

نام اصل: پلتفرم فنی یکپارچه

قانون الزام‌آور:
تمام پروژه‌های Solution باید با `.NET 10` و Target Framework برابر با `net10.0` توسعه داده شوند. استفاده از نسخه‌ای متفاوت از دات‌نت فقط پس از اصلاح رسمی Constitution مجاز است.

دلیل:
یکسان‌بودن نسخهٔ دات‌نت از ناسازگاری کتابخانه‌ها، تفاوت رفتار محیط‌ها و پیچیدگی فرایند Build و استقرار جلوگیری می‌کند.

روش بررسی:
فایل‌های پروژه و تنظیمات مشترک Build بررسی می‌شوند و فرایند CI باید در صورت مشاهدهٔ Target Framework متفاوت شکست بخورد.

## اصل دوم: رعایت جهت وابستگی در معماری Onion

نام اصل: وابستگی‌ها فقط به سمت هسته

قانون الزام‌آور:
ساختار Solution باید بر اساس معماری Onion باشد و وابستگی میان لایه‌ها فقط به سمت لایه‌های داخلی حرکت کند.

لایهٔ Domain نباید به هیچ پروژهٔ دیگری از Solution، فناوری زیرساختی، پایگاه داده، ASP.NET Core یا فریم‌ورک خارجی وابسته باشد.

لایهٔ Application از میان لایه‌های معماری فقط می‌تواند به Domain وابسته باشد و نباید به Infrastructure یا API وابستگی داشته باشد.

لایه‌های داخلی تحت هیچ شرایطی نباید به لایه‌های بیرونی Reference داشته باشند.

دلیل:
استقلال هستهٔ کسب‌وکار باعث می‌شود منطق دامنه بدون وابستگی به رابط وب، پایگاه داده یا فناوری‌های جانبی قابل توسعه و آزمون باشد.

روش بررسی:
Project Referenceهای فایل‌های `.csproj` در هر Pull Request بررسی می‌شوند و آزمون‌های معماری باید وابستگی غیرمجاز میان لایه‌ها را شناسایی کنند.

## اصل سوم: سازمان‌دهی تمام لایه‌ها بر اساس Aggregate

نام اصل: ساختار Aggregate‌محور

قانون الزام‌آور:
Aggregate باید واحد اصلی سازمان‌دهی کد در تمام لایه‌های معماری باشد. نام هر Aggregate باید در تمام لایه‌هایی که برای آن مصنوعی دارند، یکسان باشد و مصنوعات متعلق به آن Aggregate باید در پوشهٔ همان Aggregate قرار بگیرند.

برای مثال، مصنوعات Domain، Use Caseهای Application، پیاده‌سازی‌های Infrastructure و Controllerهای API مربوط به Aggregate نوشته‌ها باید زیر پوشهٔ `Posts` در لایهٔ مربوطه قرار گیرند.

ساختارهای عمومی مانند پوشه‌های سراسری `Entities`، `Services`، `Repositories` یا `Controllers` که مصنوعات چند Aggregate را با یکدیگر مخلوط می‌کنند، مجاز نیستند.

فقط مصنوعات واقعاً مشترک و مستقل از Aggregate می‌توانند در بخش `Shared` یا `Common` قرار بگیرند.

دلیل:
قرارگرفتن تمام مصنوعات یک قابلیت کسب‌وکاری زیر مرز Aggregate مربوطه، مالکیت کد را روشن و توسعه، نگهداری و یافتن اجزای مرتبط را ساده می‌کند.

روش بررسی:
در بازبینی Pull Request بررسی می‌شود که هر فایل زیر پوشهٔ Aggregate مالک آن قرار گرفته باشد، نام Aggregate در لایه‌ها یکسان باشد و پوشه‌های مشترک به محل انباشت مصنوعات نامرتبط تبدیل نشده باشند.

## اصل چهارم: استفاده از Rich Domain Model

نام اصل: دامنهٔ غنی و رفتارمحور

قانون الزام‌آور:
منطق کسب‌وکار، قواعد تغییر وضعیت و Invariantهای هر Aggregate باید در Domain و درون Aggregate Root، Entity، Value Object یا Domain Service مناسب قرار بگیرند.

وضعیت داخلی Entityها نباید مستقیماً از خارج تغییر داده شود. تغییر وضعیت باید فقط از طریق متدهای معنادار دامنه انجام شود و هیچ Aggregate نباید بتواند در وضعیت نامعتبر ایجاد یا نگهداری شود.

Entityهایی که صرفاً شامل Getter و Setter هستند و منطق کسب‌وکار آن‌ها در Application، Controller یا Infrastructure پیاده‌سازی شده است، مجاز نیستند.

دلیل:
Rich Domain Model دانش و رفتار کسب‌وکار را در محل طبیعی آن نگه می‌دارد، از پراکندگی قواعد جلوگیری می‌کند و حفاظت از Invariantها را ممکن می‌سازد.

روش بررسی:
در بازبینی کد، محل پیاده‌سازی قواعد کسب‌وکار، نحوهٔ تغییر وضعیت Entityها و حفاظت از Invariantها بررسی می‌شود. رفتارها و Invariantهای مهم هر Aggregate نیز باید آزمون واحد Domain داشته باشند.

---

## اصل پنجم: مسئولیت محدود لایهٔ Application

نام اصل: Application به‌عنوان هماهنگ‌کنندهٔ Use Case

قانون الزام‌آور:
لایهٔ Application باید Use Caseهای سیستم را تعریف و اجرای آن‌ها را هماهنگ کند، اما نباید منطق اصلی کسب‌وکار یا قواعد داخلی Aggregateها را در خود پیاده‌سازی کند.

Application می‌تواند Aggregateها را بارگذاری کند، رفتارهای Domain را فراخوانی کند، عملیات را هماهنگ کند و نتیجهٔ Use Case را برگرداند.

این لایه نباید به پیاده‌سازی پایگاه داده، Entity Framework Core، Controllerهای ASP.NET Core، جزئیات HTTP یا سایر فناوری‌های Infrastructure وابسته باشد.

دلیل:
تفکیک هماهنگی Use Case از منطق Domain، مرز مسئولیت‌ها را روشن نگه می‌دارد و امکان آزمون مستقل Application و Domain را فراهم می‌کند.

روش بررسی:
در بازبینی Use Caseها بررسی می‌شود که Application صرفاً جریان اجرا را هماهنگ کند، قواعد اصلی را به Domain بسپارد و هیچ نوع یا پیاده‌سازی متعلق به API و Infrastructure را مصرف نکند.

---

## اصل ششم: API مبتنی بر Controller

نام اصل: Controllerهای استاندارد و نازک

قانون الزام‌آور:
تمام APIهای HTTP باید با ASP.NET Core MVC Controller و کلاس‌های مشتق‌شده از `ControllerBase` پیاده‌سازی شوند. استفاده از Minimal API برای Endpointهای عمومی سیستم مجاز نیست.

Controller باید فقط مسئول دریافت و تبدیل درخواست HTTP، فراخوانی Use Case مناسب در Application و تبدیل نتیجه به پاسخ HTTP باشد.

قرار دادن منطق کسب‌وکار، دسترسی مستقیم به پایگاه داده یا مدیریت وضعیت Aggregate در Controller مجاز نیست.

دلیل:
استفادهٔ یکپارچه از Controllerها قرارداد مشخصی برای طراحی API ایجاد می‌کند و نازک نگه‌داشتن آن‌ها مانع وابستگی منطق سیستم به HTTP می‌شود.

روش بررسی:
در بازبینی مسیرهای API بررسی می‌شود که Endpointها از طریق Controller ارائه شده باشند، Controller مستقیماً به DbContext یا Repository زیرساختی دسترسی نداشته باشد و منطق کسب‌وکار در آن قرار نگرفته باشد.

## اصل هفتم: حفاظت خودکار از معماری و دامنه

نام اصل: قواعد معماری قابل‌آزمون

قانون الزام‌آور:
قواعد وابستگی لایه‌ها و Invariantهای مهم Domain باید تا حد امکان با آزمون خودکار محافظت شوند.

آزمون‌های معماری باید وابستگی غیرمجاز میان پروژه‌ها و لایه‌ها را تشخیص دهند. آزمون‌های Domain نیز باید ایجاد Aggregate، اجرای رفتارها و جلوگیری از وضعیت‌های نامعتبر را پوشش دهند.

هیچ تغییری با Build ناموفق، آزمون ناموفق یا نقض قواعد معماری نباید Merge شود.

دلیل:
بازبینی دستی به‌تنهایی نمی‌تواند در طول زمان از معماری محافظت کند. آزمون‌های خودکار، نقض قواعد تثبیت‌شده را پیش از ورود به شاخهٔ اصلی آشکار می‌کنند.

روش بررسی:
تمام Buildها و آزمون‌های معماری و Domain در CI اجرا می‌شوند و موفقیت آن‌ها شرط الزامی تأیید Pull Request است.
