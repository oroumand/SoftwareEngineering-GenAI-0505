1. spec.md مرجع قطعی رفتار محصول، قواعد کسب‌وکار و معیارهای پذیرش است.

Specification یا Constitution را تغییر نده و هیچ نیازمندی محصولی جدیدی اختراع نکن.

## تصمیم‌های فنی تثبیت‌شده

- زبان و بستر اجرا: .NET 10 و ASP.NET Core
- نوع برنامه: Web API
- APIها باید با Controller پیاده‌سازی شوند؛ از Minimal API استفاده نکن.
- معماری پروژه Onion Architecture باشد.
- Domain از هیچ پروژهٔ دیگری وابستگی نگیرد.
- Application از میان پروژه‌های Solution فقط به Domain وابسته باشد.
- Infrastructure پیاده‌سازی درگاه‌های موردنیاز Application را بر عهده داشته باشد.
- API محل Composition Root و اتصال وابستگی‌ها باشد.
- مدل دامنه Rich Domain Model باشد؛ قواعد اعتبار عنوان و متن، مالکیت، انتشار، تغییر وضعیت و جلوگیری از ویرایش پست منتشرشده داخل مدل دامنه محافظت شوند.
- Post به‌عنوان Aggregate اصلی این قابلیت بررسی شود.
- ساختار پوشه‌ها در تمام لایه‌ها Aggregate-first باشد. مصنوعات مربوط به Posts ابتدا داخل پوشهٔ همان Aggregate و سپس متناسب با هر لایه بر اساس نوع مصنوع سازمان‌دهی شوند.
- Controllerها فقط مسئول دریافت درخواست، استخراج هویت جاری، فراخوانی Application و تبدیل نتیجه به پاسخ HTTP باشند و منطق کسب‌وکار نداشته باشند.
- ثبت‌نام، ورود و مدیریت حساب کاربران پیاده‌سازی نشود. این قابلیت باید هویت نویسندهٔ احرازشده را از یک انتزاع قابل‌جایگزینی دریافت کند.
- FR-018 باید با یک راهکار Optimistic Concurrency طراحی شود؛ نخستین عملیات موفق حفظ شود و عملیات متکی بر نسخهٔ قدیمی بدون بازنویسی بی‌صدای داده رد گردد.
- انتخاب دقیق Persistence Provider، سازوکار Concurrency، کتابخانه‌های آزمون و قرارداد خطا را در research.md با دلیل و گزینه‌های جایگزین ثبت کن؛ با Constitution تعارض ایجاد نکن.
