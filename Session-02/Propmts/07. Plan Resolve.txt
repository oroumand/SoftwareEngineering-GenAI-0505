فقط مصنوعات مرحلهٔ Plan قابلیت فعال را اصلاح کن تا طراحی FR-018 واقعاً تعارض مبتنی بر نسخهٔ قدیمیِ کلاینت را پوشش دهد.

Specification و Constitution را تغییر نده.
tasks.md، کد، پروژه، Migration یا Package ایجاد نکن.

مسئله:
طرح فعلی از PostgreSQL xmin برای Optimistic Concurrency استفاده می‌کند، اما قرارداد OpenAPI هیچ نسخه یا Preconditionای از کلاینت دریافت نمی‌کند. در نتیجه یک درخواست که پس از تغییر موفق دیگری به سرور برسد، ممکن است نسخهٔ جدید را بارگذاری و ناخواسته موفق شود؛ درحالی‌که باید به‌عنوان عملیات مبتنی بر نسخهٔ قدیمی رد شود.

اصلاح‌های لازم:

1. از سازوکار استاندارد HTTP ETag / If-Match استفاده کن.
   - پاسخ ایجاد Draft باید ETag نسخهٔ اولیه را برگرداند.
   - EditDraft و PublishDraft باید If-Match را به‌عنوان Precondition الزامی دریافت کنند.
   - پاسخ موفق EditDraft باید ETag نسخهٔ جدید را برگرداند.
   - مقدار ETag باید برای کلاینت opaque باشد و xmin یا جزئیات PostgreSQL را افشا نکند.
   - Domain همچنان نباید وابستگی به EF Core، PostgreSQL، xmin یا HTTP داشته باشد.

2. برای If-Match ناموجود و If-Match نامنطبق قرارداد خطای صریح، قابل‌آزمون و سازگار تعریف کن.
   - برای نسخهٔ قدیمی از `412 Precondition Failed` با ProblemDetails کنترل‌شده استفاده کن.
   - برای تعارض وضعیت Domain، مانند تلاش برای ویرایش Post منتشرشده، پاسخ `409 Conflict` باقی بماند.
   - هیچ پاسخ خطایی نباید وجود یا محتوای Draft را افشا کند.

3. فقط این مصنوعات را در صورت نیاز اصلاح کن:
   - plan.md
   - research.md
   - data-model.md
   - contracts/openapi.yaml
   - quickstart.md

4. quickstart باید یک سناریوی End-to-End از دو درخواست با ETag یکسان داشته باشد که نشان دهد دقیقاً یکی موفق می‌شود و دیگری `412` می‌گیرد.

5. پس از اصلاح، سازگاری بین Specification، Plan، مدل داده، OpenAPI و Quickstart را دوباره بررسی و گزارش کن.

تمام متن‌های انسانی فارسی باشند.
