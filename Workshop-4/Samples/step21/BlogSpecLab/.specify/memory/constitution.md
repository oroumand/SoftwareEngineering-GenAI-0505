# قانون اساسی BlogSpecLab

## اصول بنیادین

### اصل اول — توسعهٔ مبتنی بر مشخصات

- تمام قابلیت‌ها باید براساس Specification بررسی‌شده و تأییدشده توسعه یابند.
- پیش از پیاده‌سازی، رفتار مورد انتظار، محدودیت‌ها، معیارهای پذیرش و سناریوهای خطای مهم
  باید مشخص شوند.
- چرخهٔ SDD شامل Specify، Clarify، Plan، Tasks، Implement، Test و Review باید متناسب با
  نوع تغییر رعایت شود؛ Constitution بر تمام مراحل حاکم است.
- تغییر مهم رفتاری باید ابتدا در Specification ثبت شود؛ سپس اثر آن بر طراحی، وظایف،
  کد و آزمون‌ها بررسی شود.
- خروجی Coding Agent باید پیش از پذیرش از نظر انطباق با Specification و Constitution
  بررسی شود.

### اصل دوم — معماری و قواعد وابستگی

سامانه باید یکپارچه و غیرماژولار، با تفکیک روشن مسئولیت‌ها باشد. ساختار هدف Solution:

```text
BlogSpecLab/
├── BlogSpecLab.slnx
├── src/
│   ├── 01.Core/
│   │   ├── Domain/
│   │   │   └── BlogSpecLab.Core.Domain.csproj
│   │   └── Application/
│   │       └── BlogSpecLab.Core.Application.csproj
│   ├── 02.Infra/
│   │   ├── DataAccess/
│   │   │   └── BlogSpecLab.Infra.DataAccess.csproj
│   │   ├── AI/
│   │   │   └── BlogSpecLab.Infra.AI.csproj
│   │   └── Qdrant/
│   │       └── BlogSpecLab.Infra.Qdrant.csproj
│   └── 03.Endpoints/
│       └── Api/
│           └── BlogSpecLab.Endpoints.Api.csproj
├── tests/
│   └── BlogSpecLab.Tests/
└── .specify/
```

این ساختار، هدف معماری است؛ پروژه‌های AI و Qdrant فقط هنگام ایجاد نیاز واقعی ساخته شوند.

| پروژه | مسئولیت |
| --- | --- |
| `Core.Domain` | موجودیت‌ها، اشیای مقداری، قواعد و ناورداهای دامنه؛ مستقل از زیرساخت |
| `Core.Application` | موارد کاربرد، هماهنگی عملیات، مجوزهای موارد کاربرد و قرارداد سرویس‌های بیرونی |
| `Infra.DataAccess` | پیاده‌سازی Persistence، Repositoryها و دسترسی به داده‌های عملیاتی |
| `Infra.AI` | ارتباط با مدل‌های زبانی و SDK سرویس‌دهندگان |
| `Infra.Qdrant` | ارتباط با Qdrant، ذخیره‌سازی و جست‌وجوی برداری |
| `Endpoints.Api` | ورودی HTTP، قراردادهای API، پیکربندی Dependency Injection و Composition |
| `Tests` | آزمون‌های خودکار متناسب با قابلیت‌های ایجادشده |

قواعد الزام‌آور Project Reference:

1. `Core.Domain` نباید به هیچ پروژهٔ دیگری از Solution وابسته باشد.
2. `Core.Application` می‌تواند به `Core.Domain` وابسته باشد، اما نباید به Infrastructure
   یا Endpoints رفرنس بدهد.
3. پروژه‌های Infrastructure می‌توانند به `Core.Application` و در صورت نیاز `Core.Domain`
   رفرنس داشته باشند.
4. `Endpoints.Api` می‌تواند به `Core.Application` و پروژه‌های Infrastructure موردنیاز
   برای Composition رفرنس داشته باشد.
5. وابستگی چرخه‌ای و وابستگی مستقیم میان پروژه‌های Infrastructure، بدون تصمیم معماری
   مستند، ممنوع است.
6. منطق کسب‌وکار نباید در Endpoints یا Infrastructure تکرار شود.
7. استفاده از ساختار Modules، معماری Microservices، ZaminX یا Building Blockهای اختصاصی
   سایر پروژه‌ها مجاز نیست.
8. پروژه‌ها و انتزاع‌های جدید فقط با نیازمندی تأییدشده‌ای که وجودشان را توجیه کند ایجاد شوند.

### اصل سوم — امنیت و مرز مسئولیت‌ها

- قواعد کسب‌وکار و ناورداهای وضعیت موجودیت‌ها باید در Domain یا Application اعمال شوند.
- مجوزها و پیش‌شرط‌های عملیات حساس باید در مسیر قابل اعتماد نرم‌افزار کنترل شوند؛
  Application باید تأییدهای لازم برای عملیات حساس و تغییردهنده را بررسی کند.
- خروجی مدل زبانی، آرگومان‌های Tool و داده‌های بازیابی‌شده از منابع بیرونی غیرقابل اعتمادند
  و باید متناسب با کاربرد اعتبارسنجی شوند.
- مدل زبانی یا Agent نباید صرفاً براساس خروجی خودش مجوز تغییر وضعیت سیستم را ایجاد کند.
- اطلاعات محرمانه و API Keyها نباید در کد منبع یا Logها ثبت شوند.

### اصل چهارم — کیفیت و آزمون‌پذیری

- قواعد مهم Domain و موارد کاربرد Application باید آزمون خودکار داشته باشند؛ آزمون‌ها
  باید متناسب با رفتار قابلیت، موفقیت، شکست، شرایط مرزی و دسترسی غیرمجاز را پوشش دهند.
- آزمون قواعد Domain و هماهنگی موارد کاربرد Application باید بدون اجرای سرویس‌های بیرونی
  ممکن باشد؛ آزمون خود Integrationهای خارجی باید در سطح مناسب انجام شود.
- صحت نحوی یا ساختاری خروجی مدل زبانی نباید به‌تنهایی شاهد صحت معنایی یا کسب‌وکاری باشد.
- تکمیل هر قابلیت باید با معیار پذیرش و شواهد قابل بررسی اثبات شود.

### اصل پنجم — سادگی و توسعهٔ تدریجی

- خوانایی، سادگی و قابلیت توضیح باید بر پیچیدگی غیرضروری اولویت داشته باشند؛ ایجاد
  زودهنگام پروژه، Interface، Framework یا Abstraction بدون نیاز واقعی مجاز نیست.
- نسخهٔ اولیه باید بدون وابستگی به مدل زبانی، MCP، Agent یا Vector Database اجرا شود.
- قابلیت‌های هوش مصنوعی باید مرحله‌ای و در پاسخ به نیازمندی‌های تأییدشده اضافه شوند.
- Tool Calling و MCP باید از قابلیت‌های موجود Application استفاده کنند و نباید منطق
  کسب‌وکار مستقلی ایجاد کنند.
- در RAG، مسیر ورود و آماده‌سازی دانش باید از مسیر Retrieval و Generation جدا باشد.
- Agent باید ابزارهای کنترل‌شده، محدودیت تعداد مراحل، شرایط توقف و تأیید انسانی موردنیاز
  داشته باشد.
- مدل‌ها، SDKها و Frameworkهای AI باید هنگام نیاز واقعی و پس از بررسی محدودیت‌ها و
  پیامدهای معماری انتخاب شوند.

### اصل ششم — حاکمیت و مدیریت تغییر Constitution

- Constitution مرجع اصول پایدار و الزام‌آور توسعهٔ پروژه است.
- تغییر اصول باید دلیل مشخص و بررسی اثر بر Specificationها، طراحی، کد و آزمون‌ها داشته باشد.
- تعارض Specification یا Plan با Constitution باید پیش از پیاده‌سازی برطرف شود.
- هر تغییر Constitution باید با نسخه، تاریخ تغییر و خلاصهٔ تغییرات ثبت شود.
- استثنای هر اصل باید با دلیل، پیامدها و تأیید صریح مستند شود.
- مستندات باید تصمیم‌های تأییدشده و وضعیت واقعی پروژه را منعکس کنند؛ قابلیت برنامه‌ریزی‌شده
  نباید به‌عنوان قابلیت پیاده‌سازی‌شده معرفی شود.

## معرفی و محدودیت‌های پروژه

BlogSpecLab سامانه‌ای یکپارچه برای مدیریت و انتشار پست‌های وبلاگ است. هدف نسخهٔ اولیه،
مدیریت پست‌ها و انتشار کنترل‌شدهٔ محتوای تأییدشده است. Structured Output، Tool Calling،
MCP، RAG با Qdrant و Agent قابلیت‌های برنامه‌ریزی‌شده برای مراحل بعد هستند.

زبان اصلی باید C#، چارچوب ASP.NET Core و نسخهٔ هدف .NET 10 باشد. توسعه باید با روش SDD و
ابزار Spec Kit انجام شود. پایگاه دادهٔ عملیاتی، ارائه‌دهندهٔ مدل زبانی و Embedding Model
هنوز تعیین نشده‌اند؛ انتخاب آن‌ها باید هنگام نیاز و در طراحی تأییدشده ثبت شود.

## فرایند توسعه و پذیرش

پیش از Implement، Specification تأییدشده و خروجی مراحل متناسب با تغییر باید آماده و با
Constitution سازگار باشند. در Test و Review، معیارهای پذیرش، آزمون‌های مرتبط، قواعد وابستگی
و کنترل‌های امنیتی باید بررسی شوند. پذیرش تغییر منوط به شواهد تکمیل و رفع تعارض‌ها، یا ثبت
استثنای تأییدشده مطابق اصل ششم است.

## حاکمیت

اصلاح Constitution باید با پیشنهاد مستند شامل دلیل و اثر تغییر آغاز شود، تأیید صریح مالک
پروژه را دریافت کند و با ثبت نسخه، تاریخ و خلاصهٔ اصلاح نهایی شود. اثر اصلاح بر اسناد، کد
و آزمون‌های موجود باید بررسی و کارهای لازم برای انطباق ثبت شوند.

نسخه‌گذاری باید از SemVer پیروی کند: MAJOR برای حذف یا بازتعریف ناسازگار اصول، MINOR برای
افزودن اصل یا بخش یا گسترش معنادار قواعد، و PATCH برای اصلاح نگارشی یا توضیح بدون تغییر معنا.
هر بازبینی تغییر باید انطباق با Constitution و اعتبار استثناهای مرتبط را بررسی کند.
