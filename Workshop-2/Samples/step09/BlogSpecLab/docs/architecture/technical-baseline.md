# مبنای فنی BlogSpecLab

## ۱. هدف و دامنه

این سند مرجع تصمیم‌های فنی سراسری و تأییدشدهٔ BlogSpecLab و پیش‌فرض‌های معماری
برای مراحل بعدی است؛ وضعیت پیاده‌سازی یا تصمیم‌های موقت یک قابلیت را توصیف نمی‌کند.
در صورت تعارض، [Constitution](../../.specify/memory/constitution.md) مرجع بالادستی است.

این مبنا براساس اصول Constitution و تصمیم‌های تأییدشدهٔ استخراج‌شده از
[Plan قابلیت اول](../../specs/001-blog-post-management/plan.md) و
[پژوهش آن](../../specs/001-blog-post-management/research.md) ثبت شده است.
جزئیات طراحی هر قابلیت در اسناد همان قابلیت باقی می‌مانند؛ صرف ثبت یک انتخاب در Plan
به معنای پذیرش سراسری آن نیست.

## ۲. بستر و فناوری اصلی

- زبان اصلی C#، نسخهٔ هدف .NET 10 و Framework اصلی ASP.NET Core است.

## ۳. معماری و مسئولیت‌ها

ساختار پروژه‌ها و جهت وابستگی‌ها مطابق اصل دوم Constitution است؛ ساختار هدف و
قواعد Project Reference در همان مرجع نگهداری می‌شوند.

- Domain قواعد و ناورداهای کسب‌وکار را نگهداری می‌کند و مستقل از Infrastructure است.
- Application مسئول هماهنگی موارد کاربرد و کنترل Permissionهای مربوط به Use Case است.
- Infrastructure وابستگی‌های بیرونی و قراردادهای موردنیاز Application را پیاده‌سازی می‌کند.
- Endpoints مسئول ورودی و قرارداد HTTP و Composition هستند و نباید Business Logic را
  در خود نگهداری کنند.

## ۴. ذخیره‌سازی

- برای Persistence رابطه‌ای از Entity Framework Core استفاده می‌شود.
- جزئیات ORM و DbContext نباید به Domain نشت کنند.
- Database Provider سراسری هنوز تثبیت نشده است. SQLite فقط انتخاب فعلی اجرای محلی
  و آموزشی قابلیت اول است و مبنای دیتابیس کل پروژه محسوب نمی‌شود.

## ۵. امنیت

- Authentication و Authorization مسئولیت‌های مستقل‌اند؛ شناسایی هویت به‌تنهایی
  مجوز انجام عملیات ایجاد نمی‌کند.
- Permission جاری هنگام عملیات حساس باید از منبع معتبر سمت سرور بررسی شود؛
  Application کنترل مجوز مورد کاربرد را بر عهده دارد.
- ادعاهای Client، Token یا ورودی HTTP به‌تنهایی منبع حقیقت Permission نیستند.

## ۶. قراردادهای HTTP

- خطاهای HTTP با `ProblemDetails` نمایش داده می‌شوند.
- خطاهای قابل پردازش Client باید `code` پایدار داشته باشند تا پردازش آن‌ها به متن
  پیام وابسته نباشد.
- پاسخ خطا نباید جزئیات داخلی، StackTrace، Credential یا اطلاعات حساس را افشا کند.

## ۷. آزمون

- Framework اصلی آزمون xUnit است؛ برای Integration Testهای ASP.NET Core از
  `WebApplicationFactory` استفاده می‌شود.
- قواعد Domain و موارد کاربرد Application باید بدون وابستگی غیرضروری به سرویس‌های
  بیرونی قابل آزمون باشند.
- Integrationهای واقعی باید در سطح مناسب با Provider واقعی یا نزدیک به محیط واقعی
  بررسی شوند؛ انتخاب ابزار جایگزین باید بتواند رفتار مورد آزمون را معتبر بازنمایی کند.

## ۸. هم‌زمانی و تراکنش‌ها

- Use Caseهایی که اجرای آن‌ها روی وضعیت قدیمی می‌تواند نتیجهٔ کسب‌وکاری نادرست ایجاد
  کند باید Concurrency Control صریح داشته باشند.
- مکانیزم دقیق متناسب با Aggregate، Persistence Provider و قرارداد بیرونی انتخاب
  و در طراحی قابلیت ثبت می‌شود؛ `Guid Version` برای همهٔ موجودیت‌ها و `ETag/If-Match`
  برای همهٔ APIها الزام سراسری نیستند.
- تغییرات وابسته‌ای که از نظر کسب‌وکار یک عملیات واحد هستند باید در مرز تراکنشی
  مناسب به‌صورت اتمی Commit شوند.

## ۹. تصمیم‌های هنوز باز

- Database Provider نهایی پروژه هنوز انتخاب نشده است.
- Authentication Provider نهایی پروژه هنوز انتخاب نشده است؛ opaque bearer credential
  تصمیم فعلی محیط بستهٔ آموزشی قابلیت اول است و روش دائمی پروژه محسوب نمی‌شود.
- سبک سراسری Endpointها هنوز تثبیت نشده است؛ Minimal API انتخاب قابلیت اول است و
  تنها سبک مجاز API محسوب نمی‌شود.
- Model Provider و Embedding Model هنگام ورود AI/RAG و براساس نیازمندی‌های تأییدشده
  تعیین خواهند شد.

## ۱۰. نحوهٔ تغییر مبنای فنی

پیش از اجرای Plan، ایجاد Integration جدید یا تصمیم فنی سراسری، این سند باید بررسی شود.
تصمیم‌های ثبت‌شده بدون دلیل و تصمیم معماری جدید دوباره انتخاب یا جایگزین نمی‌شوند.
پیشنهاد تغییر باید دلیل، دامنه و اثر آن بر اسناد، وابستگی‌ها، کد و آزمون‌ها را روشن کند؛
پس از تأیید تصمیم معماری، این سند و مراجع متأثر به‌روز می‌شوند.

تصمیم مخصوص یک قابلیت فقط با تأیید صریح دامنهٔ سراسری آن وارد این سند می‌شود.
تغییر ناسازگار با Constitution ابتدا تابع فرایند حاکمیت همان مرجع است؛ اصلاح این سند
به‌تنهایی اصول Constitution را تغییر نمی‌دهد.
