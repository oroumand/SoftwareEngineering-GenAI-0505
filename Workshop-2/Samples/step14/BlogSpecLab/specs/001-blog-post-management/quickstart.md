# راهنمای استفاده و اعتبارسنجی

این راهنما برای اجرای آینده پس از Implementation است. اکنون Solution، پروژه، migration و ابزار provision وجود ندارند؛ هیچ Build/Test این Feature اجرا نشده است. دستورهای آن‌ها باید پس از ایجاد و بررسی واقعی ثبت شوند. این سند کد پیاده‌سازی یا مجموعهٔ کامل آزمون نیست.

## پیش‌نیاز و آماده‌سازی آینده

۱. .NET 10 SDK و ابزار تعامل HTTP مانند curl یا Postman؛ HTTPS توسعهٔ معتبر. وجود SDK را می‌توان اکنون با `dotnet --list-sdks` بررسی کرد؛ این دستور ساخت Feature نیست.

۲. پس از پیاده‌سازی، راهنمای اجرایی باید دستورهای واقعی restore، migration، build، test و run را برای مسیرهای هدف [plan.md](plan.md) ثبت کند. SQLite فایل‌محور قابل نوشتن و پیکربندی HTTPS لازم است؛ secrets در user secrets یا secret storage محلی قرار گیرند. ابزار و migration فرضی را اکنون اجرا نکنید.

۳. ابزار provision اپراتوری آینده باید حداقل پنج Author، پنج Editor و یک کاربر دو نقشی با UserId و Credential مستقل ایجاد کند؛ Credential خام فقط به کاربر مربوط تحویل شود. یک Credential منقضی و یک لغوشده برای آزمون فراهم کنید. نام‌های A1، A2، E1، E2 و AE در زیر نام منطقی fixture هستند، نه حساب یا secret ثابت.

۴. همان ابزار باید بتواند مجوز Editor را بدون تغییر Credential معتبر لغو کند. هیچ مسیر API ورود، ثبت‌نام یا مدیریت نقش در این Feature وجود ندارد. نحوهٔ provision، مسیر DB و فرمان اپراتوری پس از ساخت ابزار دقیقاً در راهنمای اجرایی ثبت شوند.

۵. URL واقعی HTTPS برنامه را در `$env:BLOG_API_URL` و Credential کاربر جاری را در `$env:BLOG_ACCESS_TOKEN` از secret storage قرار دهید؛ مقدار واقعی در تاریخچه، خروجی یا repo ثبت نشود. دستورات زیر الگوی استفاده از قرارداد هستند، اکنون سرویس موجودی را فرض نمی‌کنند.

```powershell
curl.exe --silent --show-error --include "$env:BLOG_API_URL/api/author/posts" --header "Authorization: Bearer $env:BLOG_ACCESS_TOKEN"
curl.exe --silent --show-error "$env:BLOG_API_URL/api/posts"
```

برای درخواست JSON در Postman از Body/raw/JSON و برای mutation از If-Match استفاده کنید. UUID و ETag را از پاسخ واقعی بگیرید. `title` و `body` تنها فیلدهای ایجاد و ویرایش‌اند؛ قالب کامل در [قرارداد API](contracts/http-api.md) است.

## مسیر اصلی نویسنده و ویراستار

| گام | کاربر و عملیات | نتیجهٔ مورد انتظار |
| --- | --- | --- |
| ۱ | A1: POST author/posts با عنوان و متن معتبر | 201؛ Draft، مالک A1، Location و ETag؛ در فهرست عمومی نیست |
| ۲ | A1: GET جزئیات و PUT با If-Match جاری | 200؛ متن جدید و Version تازه |
| ۳ | A1: POST submit با ETag تازه | PendingReview؛ صف E1 شامل پست |
| ۴ | E1: GET جزئیات و POST request-changes با reason | ChangesRequested؛ A1 دلیل را می‌بیند |
| ۵ | A1: ویرایش، سپس ارسال با ETag جاری هر گام | PendingReview با محتوای اصلاح‌شده |
| ۶ | E1: GET و POST approve با ETag جاری | Approved؛ تأییدکننده/زمان/نسخه مشخص؛ هنوز عمومی نیست |
| ۷ | E1 یا E2: GET و POST publish با ETag جاری | Published؛ زمان و هویت نخست مشخص |
| ۸ | ناشناس: GET api/posts و جزئیات | فقط محتوای Published؛ بدون اطلاعات مدیریتی |
| ۹ | Editor مجاز: publish مجدد | 200؛ همان اطلاعات انتشار نخست و بدون تغییر Version |

پیش از mutation، آخرین ETag جزئیات یا پاسخ موفق را بگیرید. 412 یعنی ابتدا وضعیت را دوباره بخوانید و دربارهٔ اقدام تصمیم بگیرید؛ 409 یعنی اقدام با وضعیت فعلی سازگار نیست؛ 403 یعنی مجوز یا شرط شخص تصمیم‌گیرنده برقرار نیست. `allowedActions` راهنماست و مجوز درخواست بعدی را تضمین نمی‌کند.

## سناریوهای شکست و امنیت

- A2 جزئیات مدیریتی، ویرایش، حذف یا ارسال پست A1 را امتحان کند: 404 یا در نبود نقش مسیر 403؛ محتوا و وضعیت ثابت، بدون افشای محتوای خصوصی.
- عنوان/متن whitespace، دلیل برگشت خالی، status/ownerId/role اضافی یا If-Match نامعتبر: 400؛ داده ثابت. نبود If-Match: 428.
- بدون Credential، Credential جعلی، منقضی یا لغوشده: 401. جعل header نقش یا مالکیت مجوز ایجاد نمی‌کند.
- انتشار Draft، ChangesRequested و PendingReview حتی با Editor مجاز: 409 و عدم انتشار عمومی.
- پس از تأیید، A1 عنوان یا متن را تغییر دهد: Draft و تأیید قدیمی نامعتبر؛ انتشار رد شود. ارسال و تأیید تازه مسیر انتشار را باز کند.
- E1 تأیید کند؛ مجوز خودش لغو شود؛ با Credential هنوز معتبر انتشار درخواست کند: 403. E2 با مجوز فعلی همان تأیید تاریخی را منتشر کند: موفق.
- AE پست خود را ارسال و تأیید کند: self_approval_forbidden. E2 تأیید کند؛ AE با مجوز فعلی انتشار منتشر کند: موفق.
- A1 پست منتشرنشده را در هر وضعیت حذف کند: 204 و خروج از صف و گردش کار؛ GET و درخواست انتشار بعدی 404.
- پس از انتشار، مالک و Editor و کاربر دو نقشی ویرایش یا حذف کنند: رد؛ زمان، منتشرکننده، متن و وضعیت ثابت.
- ناشناس با شناسهٔ تمام وضعیت‌های منتشرنشده و حذف‌شده GET عمومی بزند: 404 بدون عنوان/متن/تصمیم خصوصی.

## رقابت و شواهد خودکار آینده

Domain: تمام انتقال‌ها، متن/دلیل غیرخالی، ابطال تأیید، ممنوعیت خودتأییدی و Published ثابت. Application: مجوز جاری، مالکیت، عدم اعتماد به ادعا و rollback. HTTP: handler واقعی، DTO، status/error، عدم افشای محتوا و ETag.

برای provider از دو DbContext/connection مستقل روی فایل SQLite موقت استفاده شود؛ هر دو ابتدا Version مشترک را مشاهده کنند و Commitها به‌ترتیب کنترل‌شده انجام شوند. هر دو ترتیب edit/approve، edit/publish، delete/publish و دو تصمیم بررسی را پوشش دهید. فقط انتقال سازگار موفق شود؛ شکست هیچ ReviewDecision یا Publication یتیم نگذارد. دو publish باید یک انتشار نخست داشته باشند؛ قفل DB که نهایتاً آزاد نمی‌شود، 503 بدون اثر جزئی دارد. تست بدون sleep یا retry خودکار فرمان تجاری انجام شود. تغییر مجوز اپراتوری و تراکنش حساس نیز با ترتیب کنترل‌شده آزمون شوند.

پس از عبور آزمون‌های مرتبط، شواهد SC-001، SC-002، SC-003 و SC-006 با پاسخ HTTP و وضعیت ذخیره‌شده ارائه شوند؛ token و متن خصوصی در Log آزمون چاپ نشود. در مرحلهٔ Plan فقط طراحی این بررسی‌ها انجام شده است.

## پذیرش انسانی

برای SC-004 و SC-005 حداقل پنج Author و پنج Editor با همین راهنما و ابزار API کار کنند. حداقل ۹۰٪ باید وظیفهٔ نقش خود را بدون کمک تکمیل کنند و حداقل ۹۰٪ وضعیت و اقدام بعدی را درست تشخیص دهند. تعداد موفق‌ها، خطاهای فهم و شرایط اجرا ثبت شوند؛ آزمون خودکار جای این ارزیابی را نمی‌گیرد. نبود SLA یا هدف ظرفیت، مجوز ساخت معیار کارایی جدید نیست.
