`$speckit-constitution`

برای پروژهٔ BlogSpecLab، سند Constitution را براساس اصول زیر و با استفاده از قالب استاندارد Spec Kit ایجاد کن.

تمام محتوای سند باید به زبان فارسی باشد. نام پروژه‌ها، فناوری‌ها، مسیر فایل‌ها و اصطلاحات فنی ضروری می‌توانند انگلیسی باقی بمانند.

هدف، ایجاد یک سند کوتاه، دقیق، الزام‌آور و قابل بررسی است؛ نه تولید یک مستند طولانی شامل جزئیات پیاده‌سازی.

## معرفی پروژه

BlogSpecLab یک سامانهٔ یکپارچه برای مدیریت و انتشار پست‌های وبلاگ است.

در نسخهٔ اولیه، سامانه قابلیت مدیریت پست‌ها و انتشار کنترل‌شدهٔ محتوای تأییدشده را خواهد داشت.

در مراحل بعد، قابلیت‌هایی مانند Structured Output، Tool Calling، MCP، RAG با Qdrant و Agent به‌صورت تدریجی به همین پروژه اضافه می‌شوند.

زبان اصلی C#، چارچوب ASP.NET Core و نسخهٔ هدف .NET 10 است.

پروژه با روش SDD و ابزار Spec Kit توسعه داده می‌شود.

## اصل اول — توسعهٔ مبتنی بر مشخصات

۱. تمام قابلیت‌ها باید براساس Specification بررسی‌شده و تأییدشده توسعه پیدا کنند.

۲. پیش از پیاده‌سازی، رفتار مورد انتظار، محدودیت‌ها، معیارهای پذیرش و سناریوهای خطای مهم باید مشخص شوند.

۳. چرخهٔ SDD شامل Specify، Clarify، Plan، Tasks، Implement، Test و Review متناسب با نوع تغییر رعایت شود. Constitution اصول حاکم بر تمام این مراحل را تعیین می‌کند.

۴. تغییرات مهم رفتاری باید ابتدا در Specification منعکس شوند و سپس اثر آن‌ها بر طراحی، وظایف، کد و آزمون‌ها بررسی شود.

۵. خروجی‌های Coding Agent باید قبل از پذیرش از نظر انطباق با Specification و اصول Constitution بررسی شوند.

## اصل دوم — معماری و قواعد وابستگی

پروژه باید به‌صورت یک سامانهٔ یکپارچه و غیرماژولار با تفکیک روشن مسئولیت‌ها توسعه یابد.

ساختار هدف Solution به شکل زیر است:

```text
BlogSpecLab/
├── BlogSpecLab.slnx
├── src/
│   ├── 01.Core/
│   │   ├── Domain/
│   │   │   └── BlogSpecLab.Core.Domain.csproj
│   │   └── Application/
│   │       └── BlogSpecLab.Core.Application.csproj
│   ├── 02.Infra/
│   │   ├── DataAccess/
│   │   │   └── BlogSpecLab.Infra.DataAccess.csproj
│   │   ├── AI/
│   │   │   └── BlogSpecLab.Infra.AI.csproj
│   │   └── Qdrant/
│   │       └── BlogSpecLab.Infra.Qdrant.csproj
│   └── 03.Endpoints/
│       └── Api/
│           └── BlogSpecLab.Endpoints.Api.csproj
├── tests/
│   └── BlogSpecLab.Tests/
└── .specify/
```

این ساختار، معماری هدف است. پروژه‌های مرتبط با AI و Qdrant فقط هنگام ایجاد نیاز واقعی ساخته شوند.

مسئولیت پروژه‌ها:

- `Core.Domain`: موجودیت‌ها، اشیای مقداری، قواعد و ناورداهای دامنه؛ مستقل از زیرساخت.
- `Core.Application`: موارد کاربرد، هماهنگی عملیات، کنترل مجوزهای مرتبط با موارد کاربرد و تعریف قراردادهای سرویس‌های بیرونی.
- `Infra.DataAccess`: پیاده‌سازی Persistence و Repositoryها و جزئیات دسترسی به داده‌های عملیاتی.
- `Infra.AI`: پیاده‌سازی ارتباط با مدل‌های زبانی و SDK سرویس‌دهندگان.
- `Infra.Qdrant`: پیاده‌سازی ارتباط با Qdrant و عملیات ذخیره‌سازی و جست‌وجوی برداری.
- `Endpoints.Api`: نقطهٔ ورود HTTP، قراردادهای API، پیکربندی Dependency Injection و Composition.
- `Tests`: آزمون‌های خودکار متناسب با قابلیت‌های ایجادشده.

قواعد الزام‌آور Project Reference:

۱. `Core.Domain` نباید به هیچ پروژهٔ دیگری از Solution وابسته باشد.

۲. `Core.Application` می‌تواند به `Core.Domain` وابسته باشد، اما نباید به Infrastructure یا Endpoints رفرنس بدهد.

۳. پروژه‌های Infrastructure می‌توانند به `Core.Application` و در صورت نیاز `Core.Domain` رفرنس داشته باشند.

۴. `Endpoints.Api` می‌تواند به `Core.Application` و پروژه‌های Infrastructure موردنیاز برای Composition رفرنس داشته باشد.

۵. وابستگی چرخه‌ای و وابستگی مستقیم میان پروژه‌های Infrastructure، بدون تصمیم معماری مستند، ممنوع است.

۶. منطق کسب‌وکار نباید در Endpoints یا Infrastructure تکرار شود.

۷. استفاده از ساختار Modules، معماری Microservices، ZaminX یا Building Blockهای اختصاصی سایر پروژه‌ها در این پروژه مجاز نیست.

۸. پروژه‌ها و انتزاع‌های جدید فقط زمانی ایجاد شوند که نیازمندی تأییدشده‌ای وجود آن‌ها را توجیه کند.

## اصل سوم — امنیت و مرز مسئولیت‌ها

۱. قواعد کسب‌وکار و ناورداهای مربوط به وضعیت موجودیت‌ها باید در Domain یا Application اعمال شوند.

۲. کنترل مجوزها و پیش‌شرط‌های عملیات حساس باید در مسیر قابل اعتماد نرم‌افزار اجرا شود.

۳. خروجی مدل زبانی، آرگومان‌های Tool و اطلاعات بازیابی‌شده از منابع بیرونی دادهٔ غیرقابل اعتماد محسوب می‌شوند و باید متناسب با کاربرد اعتبارسنجی شوند.

۴. هیچ مدل زبانی یا Agent نباید صرفاً براساس خروجی خودش مجوز تغییر وضعیت سیستم را ایجاد کند.

۵. عملیات حساس و تغییردهنده باید تأییدهای لازم را در Application بررسی کنند.

۶. اطلاعات محرمانه و API Keyها نباید در کد منبع یا Logها ثبت شوند.

## اصل چهارم — کیفیت و آزمون‌پذیری

۱. قواعد مهم Domain و موارد کاربرد Application باید با آزمون‌های خودکار بررسی شوند.

۲. آزمون‌ها باید متناسب با رفتار قابلیت، سناریوهای موفق، ناموفق، شرایط مرزی و دسترسی غیرمجاز را پوشش دهند.

۳. منطق Domain و Application باید تا حد امکان مستقل از اجرای سرویس‌های بیرونی قابل آزمون باشد.

۴. Integrationهای خارجی باید در سطح مناسب آزمون شوند.

۵. صحت نحوی یا ساختاری خروجی مدل زبانی به‌تنهایی به‌معنای صحت معنایی یا کسب‌وکاری آن نیست.

۶. هر قابلیت باید معیار پذیرش و شواهد قابل بررسی برای تأیید تکمیل داشته باشد.

## اصل پنجم — سادگی و توسعهٔ تدریجی

۱. خوانایی، سادگی و قابلیت توضیح بر پیچیدگی غیرضروری اولویت دارند.

۲. از ایجاد زودهنگام پروژه‌ها، Interfaceها، Frameworkها و Abstractionهای بدون نیاز واقعی خودداری شود.

۳. نسخهٔ اولیهٔ نرم‌افزار باید بدون وابستگی به مدل زبانی، MCP، Agent یا Vector Database قابل اجرا باشد.

۴. قابلیت‌های هوش مصنوعی باید در پاسخ به نیازمندی‌های تأییدشده و به‌صورت مرحله‌ای اضافه شوند.

۵. Tool Calling و MCP باید از قابلیت‌های موجود Application استفاده کنند و منطق کسب‌وکار مستقلی ایجاد نکنند.

۶. در بخش RAG، مسیر ورود و آماده‌سازی دانش از مسیر Retrieval و Generation جدا باشد.

۷. Agent باید از ابزارهای کنترل‌شده، محدودیت تعداد مراحل، شرایط توقف و تأیید انسانی موردنیاز استفاده کند.

۸. انتخاب مدل‌ها، SDKها و Frameworkهای AI باید هنگام ایجاد نیاز واقعی و با بررسی محدودیت‌ها و پیامدهای معماری انجام شود.

## اصل ششم — حاکمیت و مدیریت تغییر Constitution

۱. Constitution مرجع اصول پایدار و الزام‌آور توسعهٔ پروژه است.

۲. هر تغییر در اصول Constitution باید با دلیل مشخص و بررسی اثر آن بر Specificationها، طراحی، کد و آزمون‌ها انجام شود.

۳. تعارض میان یک Specification یا Plan و Constitution باید پیش از پیاده‌سازی برطرف شود.

۴. تغییر Constitution باید با ثبت نسخه، تاریخ تغییر و خلاصهٔ تغییرات همراه باشد.

۵. اگر رعایت یکی از اصول در شرایطی خاص امکان‌پذیر نباشد، استثنا باید با دلیل، پیامدها و تأیید صریح مستند شود.

۶. مستندات باید منعکس‌کنندهٔ تصمیم‌های تأییدشده و وضعیت واقعی پروژه باشند؛ قابلیت‌های برنامه‌ریزی‌شده نباید به‌عنوان قابلیت‌های پیاده‌سازی‌شده معرفی شوند.

## الزامات خروجی

- از ساختار استاندارد سند Constitution در Spec Kit استفاده کن.
- اصول شش‌گانهٔ بالا را حفظ کن و توضیحات تکراری یا غیرضروری اضافه نکن.
- متن نهایی باید فارسی، روشن، الزام‌آور و قابل بررسی باشد.
- نام پروژه‌ها، ساختار پوشه‌ها و قواعد Project Reference باید بدون تغییر حفظ شوند.
- موارد قطعی‌نشده مانند پایگاه دادهٔ عملیاتی، ارائه‌دهندهٔ مدل زبانی و Embedding Model را انتخاب نکن.
- سند را در مسیر `.specify/memory/constitution.md` ایجاد یا به‌روزرسانی کن.
- اگر بین اصول تناقض یا ابهام مهمی وجود دارد، آن را گزارش کن.

## محدودیت اجرای فعلی

در این مرحله فقط Constitution را تولید کن.

هیچ Solution، پروژهٔ C#، API، Specification قابلیت، Plan، Task یا کد اجرایی ایجاد نکن.

هیچ Package یا SDK نصب نکن.

اگر فرایند استاندارد Spec Kit نیازمند تغییر فایلی خارج از Constitution بود، ابتدا تغییر پیشنهادی و دلیل آن را گزارش بده و تأیید بگیر.

در پایان، فقط خلاصه‌ای از سند تولیدشده، مسیر فایل تغییر‌یافته و ابهام‌های احتمالی ارائه بده.
