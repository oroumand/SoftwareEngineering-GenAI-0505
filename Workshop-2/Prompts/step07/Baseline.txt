## تصمیم‌های سراسری تأییدشده

موارد زیر باید در Technical Baseline ثبت شوند:

### Platform

- زبان اصلی پروژه C# است.
- نسخهٔ هدف .NET 10 است.
- Framework اصلی ASP.NET Core است.

### Architecture

- ساختار پروژه‌ها و جهت وابستگی‌ها مطابق Constitution است.
- Domain باید مستقل از Infrastructure باقی بماند.
- Application مسئول Orchestration موارد کاربرد و کنترل Permissionهای مربوط به Use Case است.
- Infrastructure مسئول پیاده‌سازی وابستگی‌های بیرونی است.
- Endpoints نباید Business Logic را در خود نگهداری کنند.

### Persistence

- برای Persistence رابطه‌ای پروژه از Entity Framework Core استفاده می‌شود.
- Provider دیتابیس سراسری پروژه هنوز تثبیت نشده است.
- SQLite فقط انتخاب فعلی برای اجرای محلی و آموزشی Feature اول است و نباید به‌عنوان Database Baseline کل پروژه ثبت شود.
- جزئیات ORM و DbContext نباید به Domain نشت کنند.

### Security

- Authentication و Authorization دو مسئولیت مستقل هستند.
- شناسایی هویت کاربر به‌تنهایی مجوز عملیات ایجاد نمی‌کند.
- Permission جاری باید هنگام عملیات حساس از منبع معتبر سمت سرور بررسی شود.
- ادعاهای Client، Token یا ورودی HTTP نباید به‌تنهایی Source of Truth برای Permission باشند.

### HTTP Error Contract

- خطاهای HTTP باید با `ProblemDetails` نمایش داده شوند.
- خطاهای قابل پردازش Client باید دارای `code` پایدار باشند.
- جزئیات داخلی، StackTrace، Credential و اطلاعات حساس نباید در پاسخ خطا افشا شوند.

### Testing

- Framework اصلی آزمون پروژه xUnit است.
- برای Integration Testهای ASP.NET Core از `WebApplicationFactory` استفاده می‌شود.
- قواعد Domain و Application باید بدون وابستگی غیرضروری به سرویس‌های بیرونی قابل آزمون باشند.
- Integrationهای واقعی باید در سطح مناسب و با Provider واقعی یا نزدیک به محیط واقعی بررسی شوند.

### Concurrency و Atomicity

- Use Caseهایی که اجرای آن‌ها روی وضعیت قدیمی می‌تواند نتیجهٔ کسب‌وکاری نادرست ایجاد کند باید Concurrency Control صریح داشته باشند.
- مکانیزم دقیق Concurrency می‌تواند متناسب با Aggregate، Persistence Provider و قرارداد بیرونی انتخاب شود.
- استفاده از Guid Version یا ETag نباید به‌صورت قاعدهٔ اجباری برای تمام موجودیت‌های آینده ثبت شود.
- تغییرات وابسته‌ای که از نظر کسب‌وکار یک عملیات واحد هستند باید در مرز تراکنشی مناسب به‌صورت اتمی Commit شوند.

## مواردی که نباید Baseline شوند

موارد زیر فقط تصمیم‌های Feature فعلی یا محیط آموزشی هستند و نباید به تصمیم سراسری تبدیل شوند:

- SQLite به‌عنوان دیتابیس اصلی پروژه
- Minimal API به‌عنوان تنها سبک مجاز API
- opaque bearer credential به‌عنوان روش دائمی Authentication
- Guid Version برای تمام Aggregateها
- ETag/If-Match برای تمام APIهای آینده

در صورت نیاز می‌توان در Technical Baseline توضیح داد که این موارد فعلاً تصمیم سراسری نیستند.

- Model Provider و Embedding Model در زمان ورود AI/RAG تعیین خواهند شد.
