## اصل دوم: رعایت جهت وابستگی در معماری Onion

نام اصل: وابستگی‌ها فقط به سمت هسته

قانون الزام‌آور:

ساختار Solution باید (`MUST`) بر اساس معماری Onion باشد و وابستگی میان لایه‌های تولید فقط به سمت لایه‌های داخلی حرکت کند.

قواعد وابستگی لایه‌ها به شرح زیر است:

* لایهٔ Domain نباید (`MUST NOT`) به هیچ پروژهٔ دیگری از Solution، Package خارجی، فناوری زیرساختی، پایگاه داده، ASP.NET Core یا فریم‌ورک جانبی وابسته باشد و فقط می‌تواند از امکانات استاندارد دات‌نت استفاده کند.
* لایهٔ Application از میان پروژه‌های Solution فقط می‌تواند (`MAY`) به Domain وابسته باشد و نباید (`MUST NOT`) به Infrastructure، API یا Host وابستگی داشته باشد.
* لایهٔ Infrastructure می‌تواند (`MAY`) برای پیاده‌سازی Portها و قراردادها به Application و Domain وابسته باشد، اما نباید (`MUST NOT`) به API یا Host وابسته شود.
* پروژهٔ API یا Host به‌عنوان Composition Root می‌تواند (`MAY`) برای ثبت و اتصال وابستگی‌ها به Application و Infrastructure Reference داشته باشد.
* Controllerها و سایر اجزای ارائهٔ API نباید (`MUST NOT`) مستقیماً نوع Concrete متعلق به Infrastructure دریافت یا مصرف کنند و باید از طریق Use Caseها و قراردادهای Application با سیستم تعامل داشته باشند.
* پروژه‌های Test می‌توانند (`MAY`) به لایهٔ تحت آزمون و کتابخانه‌های آزمون وابسته باشند و جزئی از گراف وابستگی کد تولید محسوب نمی‌شوند.

هیچ لایهٔ داخلی نباید (`MUST NOT`) برای دسترسی به قابلیت‌های یک لایهٔ بیرونی، Reference معکوس ایجاد کند. ارتباط با فناوری‌ها و سرویس‌های بیرونی باید از طریق قراردادهای تعریف‌شده در لایهٔ مناسب و پیاده‌سازی آن‌ها در Infrastructure انجام شود.

دلیل:

استقلال هستهٔ کسب‌وکار باعث می‌شود منطق Domain و Use Caseهای سیستم بدون وابستگی به رابط وب، پایگاه داده یا فناوری‌های جانبی قابل توسعه، آزمون و نگهداری باشند.

روش بررسی:

Project Referenceها، Package Referenceهای Domain و وابستگی Namespaceها در هر Pull Request بررسی می‌شوند. آزمون‌های معماری خودکار باید تمام وابستگی‌های غیرمجاز میان لایه‌ها را شناسایی کنند.

## اصل سوم: سازمان‌دهی تمام لایه‌ها بر اساس Aggregate

نام اصل: ساختار Aggregate‌محور

قانون الزام‌آور:

Aggregate باید (`MUST`) واحد اصلی سازمان‌دهی مصنوعات کسب‌وکاری در تمام لایه‌های معماری باشد.

نام هر Aggregate باید در تمام لایه‌هایی که برای آن مصنوعی دارند یکسان باشد و تمام مصنوعات متعلق به آن Aggregate باید در پوشهٔ همان Aggregate در لایهٔ مربوطه قرار بگیرند.

هر پوشهٔ Aggregate باید متناسب با مسئولیت لایه، زیرساختار فنی روشنی داشته باشد. برای مثال:

* در Domain، پوشه‌هایی مانند `Entities`، `ValueObjects`، `Events` و `Services`
* در Application، مصنوعات Use Case مانند Commandها، Queryها، Handlerها، DTOها و Validatorها
* در Infrastructure، پیاده‌سازی Repositoryها، نگاشت‌های Persistence و Adapterهای مرتبط
* در API، Controllerها، مدل‌های HTTP و نگاشت‌های مربوط به آن Aggregate

ساختارهای عمومی مانند پوشه‌های سراسری `Entities`، `Services`، `Repositories` یا `Controllers` که مصنوعات چند Aggregate را با یکدیگر مخلوط می‌کنند، مجاز نیستند (`MUST NOT`).

مصنوعاتی که مالکیت آن‌ها واقعاً به یک Aggregate محدود نیست، مانند Composition Root، Migrationهای سراسری، زیرساخت فنی مشترک یا فرایندهای هماهنگ‌کنندهٔ چند Aggregate، می‌توانند (`MAY`) در پوشه‌ای مستقل با نام و مسئولیت صریح قرار گیرند.

فقط مصنوعات واقعاً مشترک، پایدار و مستقل از یک Aggregate می‌توانند (`MAY`) در بخش `Shared` یا `Common` قرار بگیرند. این پوشه‌ها نباید (`MUST NOT`) برای فرار از تعیین مالکیت یا نگهداری فایل‌های بی‌ارتباط استفاده شوند.

دلیل:

قرارگرفتن مصنوعات هر قابلیت کسب‌وکاری زیر مرز Aggregate مربوطه، مالکیت کد را روشن می‌کند و توسعه، بازبینی، نگهداری و یافتن اجزای مرتبط را ساده‌تر می‌سازد.

روش بررسی:

در بازبینی Pull Request باید بررسی شود که هر مصنوع کسب‌وکاری زیر پوشهٔ Aggregate مالک خود قرار گرفته، نام Aggregate در لایه‌ها یکسان است، زیرساختار هر لایه با مسئولیت آن تناسب دارد و پوشه‌های مشترک به محل انباشت مصنوعات نامرتبط تبدیل نشده‌اند.

## اصل چهارم: استفاده از Rich Domain Model

نام اصل: دامنهٔ غنی و رفتارمحور

قانون الزام‌آور:

منطق کسب‌وکار، قواعد تغییر وضعیت و Invariantهای هر Aggregate باید (`MUST`) در Domain و درون Aggregate Root، Entity، Value Object یا Domain Service مناسب پیاده‌سازی شوند.

وضعیت داخلی Entityها و Aggregateها نباید (`MUST NOT`) مستقیماً از خارج تغییر داده شود. تغییر وضعیت باید فقط از طریق متدهای معنادار Domain انجام شود.

Aggregate باید هنگام ایجاد، داده‌های اولیهٔ خود را اعتبارسنجی کند. هیچ وضعیت نامعتبری نباید از مرز عمومی Aggregate قابل مشاهده باشد یا پس از پایان یک عملیات Domain در Aggregate باقی بماند.

Entityهای Domain که صرفاً شامل Getter و Setter هستند و منطق کسب‌وکار آن‌ها در Application، Controller یا Infrastructure پیاده‌سازی شده است، مجاز نیستند (`MUST NOT`).

Domain Service فقط زمانی مجاز است (`MAY`) که یک رفتار Domain به‌طور طبیعی متعلق به یک Entity، Value Object یا Aggregate Root مشخص نباشد. Domain Service نباید (`MUST NOT`) برای خارج‌کردن رفتار متعلق به Aggregate یا ایجاد مدل دامنهٔ کم‌رمق استفاده شود.

لایه‌های Application، Infrastructure و API نباید (`MUST NOT`) قواعد داخلی Aggregate یا Invariantهای آن را دور بزنند.

دلیل:

Rich Domain Model دانش و رفتار کسب‌وکار را در محل طبیعی آن نگه می‌دارد، از پراکندگی قواعد جلوگیری می‌کند و حفاظت متمرکز از Invariantهای سیستم را ممکن می‌سازد.

روش بررسی:

در بازبینی کد، محل پیاده‌سازی قواعد کسب‌وکار، نحوهٔ ایجاد Entityها، روش تغییر وضعیت و حفاظت از Invariantها بررسی می‌شود. هر Invariant جدید یا تغییریافته باید آزمون واحد Domain داشته باشد که هم رفتار معتبر و هم رد وضعیت نامعتبر را اثبات کند.

## اصل پنجم: مسئولیت محدود لایهٔ Application

نام اصل: Application به‌عنوان هماهنگ‌کنندهٔ Use Case

قانون الزام‌آور:

لایهٔ Application باید (`MUST`) Use Caseهای سیستم را تعریف و اجرای آن‌ها را هماهنگ کند، اما نباید (`MUST NOT`) منطق اصلی کسب‌وکار یا قواعد داخلی Aggregateها را در خود پیاده‌سازی کند.

Application می‌تواند (`MAY`) Aggregateها را از طریق قراردادها بارگذاری کند، رفتارهای Domain را فراخوانی کند، اجرای عملیات را هماهنگ کند، Portهای بیرونی را فراخوانی کند و نتیجهٔ Use Case را برگرداند.

سیاست‌های مربوط به اجرای Use Case، مانند هماهنگی تراکنش، مجوز دسترسی به Use Case، Idempotency و هماهنگی فراخوانی سرویس‌های خارجی می‌توانند (`MAY`) در Application قرار گیرند.

قواعدی که معتبر یا نامعتبر بودن یک وضعیت کسب‌وکاری را تعیین می‌کنند باید (`MUST`) در Domain قرار داشته باشند.

Application نباید (`MUST NOT`) به پیاده‌سازی پایگاه داده، Entity Framework Core، Controllerهای ASP.NET Core، جزئیات HTTP یا نوع Concrete متعلق به Infrastructure وابسته باشد.

قراردادهای موردنیاز Application برای Persistence، پیام‌رسانی یا سرویس‌های خارجی باید (`MUST`) در یک لایهٔ داخلی تعریف و توسط Infrastructure پیاده‌سازی شوند.

دلیل:

تفکیک هماهنگی Use Case از منطق Domain، مرز مسئولیت‌ها را روشن نگه می‌دارد و امکان آزمون مستقل Application و Domain را فراهم می‌کند.

روش بررسی:

در بازبینی Use Caseها باید بررسی شود که Application فقط جریان اجرا را هماهنگ می‌کند، قواعد کسب‌وکار را به Domain می‌سپارد، جزئیات فناوری را از طریق قراردادها پنهان می‌کند و هیچ نوع متعلق به API یا پیاده‌سازی Concrete زیرساخت را مصرف نمی‌کند.

## اصل ششم: API مبتنی بر Controller

نام اصل: Controllerهای استاندارد و نازک

قانون الزام‌آور:

تمام Endpointهای کسب‌وکاری HTTP باید (`MUST`) با ASP.NET Core MVC Controller و کلاس‌های مشتق‌شده از `ControllerBase` پیاده‌سازی شوند.

استفاده از Minimal API برای Endpointهای کسب‌وکاری مجاز نیست (`MUST NOT`).

Endpointهای عملیاتی که مستقیماً توسط فریم‌ورک یا زیرساخت ارائه می‌شوند، مانند Health Check، Metrics و OpenAPI، از این الزام مستثنا هستند؛ مشروط بر اینکه هیچ رفتار کسب‌وکاری ارائه نکنند.

Controller باید (`MUST`) فقط مسئول دریافت و تبدیل درخواست HTTP، اعمال اعتبارسنجی مرزی، فراخوانی Use Case مناسب در Application و تبدیل نتیجه به پاسخ HTTP باشد.

قرار دادن منطق کسب‌وکار، مدیریت مستقیم وضعیت Aggregate، دسترسی مستقیم به DbContext یا Repository زیرساختی و مصرف نوع Concrete متعلق به Infrastructure در Controller مجاز نیست (`MUST NOT`).

دلیل:

استفادهٔ یکپارچه از Controllerها قرارداد مشخصی برای طراحی API ایجاد می‌کند و نازک نگه‌داشتن آن‌ها مانع وابسته‌شدن منطق سیستم به HTTP و ASP.NET Core می‌شود.

روش بررسی:

در بازبینی مسیرهای API باید بررسی شود که Endpointهای کسب‌وکاری از طریق Controller ارائه شده‌اند، استثناها فقط ماهیت عملیاتی دارند، Controller مستقیماً به Infrastructure یا پایگاه داده دسترسی ندارد و هیچ قاعدهٔ کسب‌وکاری در آن پیاده‌سازی نشده است.

## اصل هفتم: حفاظت خودکار از معماری و دامنه

نام اصل: قواعد معماری قابل‌آزمون

قانون الزام‌آور:

تمام قواعد جهت وابستگی تعریف‌شده در Constitution باید (`MUST`) توسط آزمون‌های معماری خودکار محافظت شوند.

هر Invariant دامنه که ایجاد یا تغییر می‌کند باید (`MUST`) با آزمون واحدی پوشش داده شود که حداقل مسیر معتبر و جلوگیری از وضعیت نامعتبر را اثبات کند.

آزمون‌های Domain باید (`MUST`) ایجاد Aggregateها، اجرای رفتارهای مهم و حفاظت از Invariantها را پوشش دهند.

فرایند CI باید (`MUST`) Build، آزمون‌های Domain، آزمون‌های معماری و سایر آزمون‌های خودکار پروژه را اجرا کند.

هیچ تغییری با Build ناموفق، آزمون ناموفق یا نقض قواعد معماری نباید (`MUST NOT`) Merge شود.

غیرفعال‌کردن، حذف یا دورزدن یک آزمون برای عبور موقت از CI مجاز نیست (`MUST NOT`)، مگر اینکه رفتار یا قانون مرتبط رسماً تغییر کرده و آزمون جایگزین مناسب در همان تغییر ارائه شده باشد.

دلیل:

بازبینی دستی به‌تنهایی نمی‌تواند در طول زمان از معماری و Invariantهای Domain محافظت کند. آزمون‌های خودکار نقض قواعد تثبیت‌شده را پیش از ورود تغییرات به شاخهٔ اصلی آشکار می‌کنند.

روش بررسی:

نتیجهٔ Build و تمام مجموعه‌آزمون‌های الزامی در CI ثبت می‌شود و موفقیت همهٔ آن‌ها باید شرط لازم برای تأیید و Merge هر Pull Request باشد.

## اصل هشتم: اعتبارسنجی و امنیت در مرزهای سیستم

نام اصل: مرزهای ورودی و خروجی امن

قانون الزام‌آور:

تمام داده‌های ورودی از HTTP، پیام، فایل، پایگاه داده یا سرویس خارجی باید (`MUST`) پیش از استفاده در Use Case اعتبارسنجی شوند.

اعتبارسنجی مرزی نباید جایگزین حفاظت از Invariantهای Domain شود. Domain باید (`MUST`) مستقل از اعتبارسنجی لایه‌های بیرونی از معتبرماندن وضعیت خود محافظت کند.

تمام عملیات محافظت‌شده باید (`MUST`) احراز هویت و مجوز دسترسی صریح و قابل‌آزمون داشته باشند.

Secretها، Credentialها و داده‌های حساس نباید (`MUST NOT`) در مخزن کد یا تنظیمات قابل‌Commit نگهداری شوند.

Logها و پاسخ‌های API نباید (`MUST NOT`) Secret، Credential، Stack Trace، جزئیات داخلی پیاده‌سازی یا داده‌های حساس غیرضروری را افشا کنند.

خطاهای ورودی و دسترسی باید (`MUST`) به پاسخ‌های کنترل‌شده و بدون افشای جزئیات داخلی تبدیل شوند.

دلیل:

کنترل ورودی‌ها و خروجی‌های سیستم از ورود داده‌های مخرب یا نامعتبر، دسترسی غیرمجاز و افشای اطلاعات حساس جلوگیری می‌کند و در عین حال استقلال دفاعی Domain را حفظ می‌کند.

روش بررسی:

برای ورودی‌های نامعتبر، دسترسی‌های غیرمجاز و پاسخ‌های خطا باید آزمون خودکار وجود داشته باشد. بازبینی Pull Request باید نحوهٔ مدیریت داده‌های حساس را کنترل کند و CI باید مخزن را از نظر افشای Secret بررسی کند.
